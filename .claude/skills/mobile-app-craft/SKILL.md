# 手機 App 開發工作流程

使用者是產品擁有者而非工程師，以繁體中文溝通，會不斷「滾動調整」。他最在意四件事：**UI 編排邏輯、直觀、美術、動效**。所以每一輪交付的標準是：在手機上打開就覺得順、好看、知道下一步要按哪裡，而不只是「功能有做出來」。

## 工作循環（每一輪需求都走一次）

### 1. 理解需求
- 截圖是最主要的需求來源：逐一圈出截圖裡的所有問題（跑版、遮擋、截字、對比、不一致），通常不只一個。
- 使用者附規格書或建議文件時，逐條對照；做不到的（平台限制，例如 iOS 不允許網頁自己加入主畫面）說明原因並給最接近的替代方案。
- 需要專業知識（領域規則、法規、典籍）時先查證，回覆附來源；有爭議處標註而不自創。
- 方向不明、或是「提出改善方案」類需求，用選擇題（AskUserQuestion，附「其他」）讓使用者挑；細節慣例自己決定，不要事事都問。

### 2. 規劃（動手前）
- 先讀 `references/ui-ux.md`，用「使用者任務」決定分頁與入口：底部 3–5 個主分頁、分頁內用分段切換子功能、首頁提供快速入口。
- 新專案：用 `scripts/new_app.py` 從 `assets/starter/` 建立骨架（深淺色、分頁列、捲動收起、彈窗、更新提示、離線、加到主畫面都已內建），再往上長功能。
- 既有專案：先讀結構與既有慣例，沿用它的寫法；不要整站重寫。

### 3. 實作
- 視覺與動效依 `references/motion.md` 的時間與曲線；所有動畫尊重「減少動態」。
- 深淺色同時設計，用 CSS 變數；新樣式附加在檔尾。
- 狀態要明確：多步驟流程用狀態機（例如 intro → 進行中 → 選擇 → 揭示 → 完成），先存結果再播動畫，防重複點擊。
- 文案白話、短、具體動詞（「開始抽牌」不是「開始」）；術語附白話解釋。

### 4. 親自用一遍（不可省略）
在測試之前，**用使用者的角度把這次改動實際操作一次**：手機尺寸、從首頁出發、照著畫面提示走到結果，再試返回、重來、深色、大字級。截圖後**親眼看圖**，問自己：
- 第一次看到的人知道要按哪裡嗎？下一步明顯嗎？
- 有沒有被遮住、截斷、擠成兩行、對齊歪掉？
- 動畫有沒有幫助理解，還是只是拖時間？夠精緻嗎？
- 和 App 其他地方風格一致嗎？
發現問題就先修，修完再看一次。這一步的截圖比任何數字都重要。開工前先翻一下 `references/lessons.md`（踩過的坑），避免重犯。

### 5. 自動化測試
用 `scripts/qa.cjs`（說明見 `references/testing.md`）跑：每個頁面 × 深淺色 × 360/390 寬 × 字級 1／1.45 的截圖、溢出檢查、錯誤收集、無障礙（有 axe 時）。另外為本次改動寫專用的互動腳本（`scripts/pw.cjs` 會找到 Playwright 並啟動預裝的 Chromium）。

### 6. 發布
依 `references/release.md`：寫更新紀錄（使用者更新後會看到）→ 更新 README → build → commit／push → PR → 合併 → 確認部署 → 更新預覽。

### 7. 回報
繁體中文，先結論；分點說做了什麼、為什麼；附連結；誠實列出沒能真機驗證的部分與還沒做的建議，問下一步。

## 持續改進這個技能
每次發現新的坑，補進 `references/lessons.md`；模板或腳本本身有問題就直接修它們。使用者會不斷提出新偏好。當他糾正方向或提出可重複套用的原則（例如「動畫要更炫」「不要紅色印章」「排版留白太多」），把它整理成通則寫進 `references/ui-ux.md` 或 `motion.md` 的「使用者偏好」段落，下次直接遵守。
